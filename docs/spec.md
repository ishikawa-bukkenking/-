Chatworkの書き込みから、「受注理由」と「失注理由」が書かれている会社と理由を拾い出し、

# 1. 目的と、使い道

- 目的:受注できた理由・失注した理由を、会社ごとに一覧にして、営業の改善(トークや提案、
  Zohoの失注理由の整理)に使う
- 読む人:セールスグロース。表をもとに、理由の傾向を見る
- 元データ:Chatworkの営業・商談・受注まわりのルームの書き込み

## 1-1. 受注と失注で、理由の取り方が違う(2026-11-11 追記)

- **受注理由**:受注チャットの「受注経緯」にある **「課題感」「加盟目的」** から取る。
  決まった書式で書かれている(例:`課題感:受注減` / `加盟目的:土地仲介+新築、自社建売販売`)。
  この2項目の原文を、そのまま別々の列に持つ。理由(要約)は、この2項目だけから作る
  (受注経緯のほかの文は、理由に使わない)
- **失注理由**:決まった書式はない。文章から拾う。例:
  - 「ビジネスモデルに理解はあるが、費用とランニングが大きく、スポットで別のところにお金をかける判断」
  - 「業務量と資金的な問題が大きな懸念点。分譲地の売却目処が立ったタイミングで再検討」
  - 「宅建士の採用を優先する。人ありきで導入するかどうかの順番」
- 付ける切り口:
  - 受注:**担当者別・プラン別・リード別**
  - 失注:**担当者別・リード別**(プラン別は付けない)
- 担当者・プラン・リードは、まず**メッセージに書かれている内容**を使う。書かれていなければ、
  **会社名でZohoの商談を検索して補う**(下の1-2)。それでも分からなければ「記載なし」とし、推測で埋めない
  (「投稿者」と「担当者」は別の列。同じ人とは限らない)

## 1-2. Zohoでの補完(読み取り専用。2026-11-11 追記)

- 使うのは、検索と取得だけ。**Zohoには何も書き込まない**(作成・更新・削除をしない)
- Zohoの商談(Deals)の項目(2026-11-11に確認):
  - 担当者 = `Owner`(商談の担当者)
  - リード = `field33`(リード種別)。補助として `Lead_Source`(見込み客のデータ元)、`field21`(知ったきっかけ)
  - 取引先 = `Account_Name`、ステージ = `Stage`
  - プラン = 商談の金額 `Amount`(総額)をプランの代わりに使う(決定済み)。金額は、書かれた数字のまま持ち、
    金額帯への分け方(例:〜100万円、100〜300万円)は、実際の分布を見てから私に提案する。
    チャットにプラン名が書かれていれば、別の列に原文で残す。Zohoの金額が空・0のときは「記載なし」
  - 参考:Zohoには `field6`(受注理由)・`field7`(失注理由)の選択肢がある(下の理由カテゴリの元)。
    **Zohoの値は、チャットの理由とは別の列「Zoho受注理由/失注理由」に入れ、本表の理由に混ぜない**
- 会社名で検索して、**候補が1件**で、取引先名が一致するときだけ採用する。複数あるとき(同名・支店・
  別時期の商談)は、受注日・失注日に近い商談を選び、選び方を「Zoho照合メモ」に書く。決められなければ
  「要確認」にする
- 補完した値には、「出どころ」列に「チャット」か「Zoho」を入れる。どの商談IDかも残す
- Zohoの情報(商談ID、担当者名など)は、この作業の表だけに使う。外のサービスには送らない

2. **対象は、ルームID 242452086 と 105812703 の2つだけ。** APIトークンは、私が入っているすべての

3. **APIトークンをコード、ログ、ドキュメント、チャットに書かない。** 環境変数から読む。

4. **取ったメッセージを、外のサービスに送らない**(有料のAIのAPIや、ファイル共有サービスなど)。

5. **書いていない理由を、作らない。** メッセージに書かれている内容だけを使う。
   理由が書かれていなければ、理由は「記載なし」とし、推測で埋めない。
   「たぶんこうだろう」は、別の列(推測メモ)に分け、本表の理由には入れない
6. 元のメッセージの文は、**加工せずに保存**する。要約や分類は、別の列に持つ
7. 取った生データは、私のパソコンの作業フォルダの中に置き、リポジトリや共有フォルダには入れない
   (.gitignoreに入れる)。顧客の情報が含まれるため
8. 分からないことは、推測で進めず、質問する

# 5. 拾い出し(2段階)

## 5-1. 候補を絞る(コードで。機械的に)

メッセージ全体から、**理由が書かれていそうな書き込み**を、キーワードで拾う。拾い漏れを減らすため、
広めに拾い、あとで絞る。

- **受注の書式を最優先**:「課題感」「加盟目的」「受注経緯」を含む投稿は、すべて候補にする。
- 区分のヒント(受注側):受注、成約、契約、お申し込み、申込、決まり、決定、決め手、採用、導入が決まった、
  ご契約いただき
- 区分のヒント(失注側):**「お見送り」「見送り」が、失注の書き方として最も多い**(私の見立て)。
  これを最優先の目印にして、「見送り」を含む投稿は、すべて候補にする(「見送り」の活用形も:
  見送る、見送りに、見送りとなり、見送りたい、お見送りいただき、など)。
  そのほか:失注、辞退、断られ、ご縁がなかった、NG、他社、競合、今回は難しい、白紙、キャンセル、不採択(補助金)
- **「見送り」の意味に注意**:失注(お客様が見送った)と、こちらが見送った(提案を見送る、
  次回に見送る、日程の見送り、投稿・配信の見送り、など)がある。主語と文脈を読んで、
  商談の結果としてお客様が見送った場合だけを「失注」にする。それ以外は「対象外」か「保留・検討中」にし、
  迷う場合は「判断できない」に回す。
  「見送り」を含む候補の数と、そのうち失注にしたもの・しなかったものの内訳を、報告する
- 理由のヒント:理由、決め手、ポイント、ネック、懸念、価格、費用、高い、安い、予算、時期、タイミング、
  決裁、社長、役員、比較、相見積、補助金、実績、担当、提案、サイト、システム
- 候補にしたら、**前後の文脈**も一緒に持つ:同じルームの前後5件、返信の連鎖、同じ投稿者の連続した投稿
  (理由が、次の投稿に分かれて書かれることがあるため)
- 候補の数と、キーワードごとの件数を報告する(キーワードが広すぎる/狭すぎるかを、私と見直す)

## 5-2. 読んで、表にする(あなた自身が、読んで判断する)

候補ごとに、次のどれかに分ける。

| 区分 | 意味 |
|------|------|
| 受注 | 受注・成約・申込の報告で、理由(決め手)が書かれている |
| 失注 | 失注・見送りの報告で、理由が書かれている |
| 保留・検討中 | まだ決まっていない。理由や懸念が書かれている(参考) |
| 対象外 | 受注/失注の理由の話ではない(雑談、日程調整、資料送付、など) |
| 判断できない | 文脈が足りない(要確認に回す) |

- 「失注」は、商談の結果としての失注。**補助金の不採択は、失注とは別**に扱い、
  理由のカテゴリ(補助金)として残す(不採択が原因で失注した場合は、その旨を理由に書く)
- **解約・休会・退会**の話は、今回の対象外。ただし、見つけたら、別シート「参考(解約・休会)」に分けて残す
- 1つの書き込みに、複数の会社が出てくる場合は、会社ごとに1行に分ける
- 同じ会社の、同じ結果の書き込みが、複数ある場合(報告→追記→再掲)は、
  **1行にまとめ、メッセージIDは全部残す**。理由が増えている場合は、足していく。
  違う結果(例:失注→後日受注)は、別の行にする
- 理由は、**書かれている言葉に忠実に、短く**まとめる(1〜2文)。原文の短い引用も、別の列に入れる

# 7. 集計と分析

## 7-1. 集計(シート2「集計」。数えるだけ)

- 区分(受注/失注/保留・検討中)ごとの件数。ルームごと、期ごと(11月〜10月)、月ごと
- 区分 × 理由カテゴリの件数(受注と失注を並べて見られる形)。1件に複数カテゴリがある場合は、

- 「記載なし」(理由が書かれていない)の件数と割合。報告の書き方の抜けとして、見えるようにする
- 同じ会社の、結果の移り変わり(例:失注 → 後日受注)の一覧

## 7-2. 分析(新しいシート「分析」と、短い報告書 `analysis.md`)

次の問いに、表の数字で答える。

0. **受注の課題感・加盟目的は、何が多いか。** 原文の言い回しの上位(課題感と加盟目的を、別々に)
1. **失注の理由は、何が多いか。** 理由カテゴリの順位と、代表的な言い回し(原文の抜粋つき)
2. **受注の決め手は、何が多いか。** 失注の理由と、並べて比べる(同じカテゴリで、受注と失注のどちらに
   多く出るか)
3. **「お見送り」の中身。** お見送りと書かれた失注を、理由の書き方で分ける
   (理由つき / 「お見送り」とだけ書かれている / 理由は別の投稿)。理由が書かれていない割合が高ければ、
   それ自体を、報告の改善点として挙げる
4. **時期の傾向。** 月・期ごとの、受注と失注の件数と理由の変化(件数が少ない場合は、傾向とは言わない)
5. **担当者・リード・プランごとの違い**:受注は担当者別・プラン別・リード別、失注は担当者別・リード別。
   「記載なし」の件数も併記する。各区分が5件未満なら「少数のため参考」
6. **気づいたこと(解釈)**。営業の改善につながりそうな点を、3〜5個。それぞれ、根拠の件数と、
   原文の抜粋を付ける

分析で守ること:

- **件数が少ないときは、割合や傾向を断定しない。** 各カテゴリの件数が5件未満のときは、
  「少数のため参考」と書く。パーセントは、件数を併記する
- **この表は「Chatworkに理由が書かれた案件」だけ**で、全商談ではない。したがって、
  「失注率」「受注率」は、この表からは出さない(分母が分からないため)。
  Zohoの商談数などと比べたい場合は、別途、私に聞く
- 書かれた理由は、お客様が本当に思っていることではなく、**営業が書いた理由**。この限界を、報告書の最初に書く
- 原因を断定しない(「価格が高いから失注した」ではなく、「失注の理由として、価格が書かれた件が最多だった」)
- 改善案は、「提案」として書き、根拠の数字と並べる
- 図は、見やすさを優先して、棒グラフ(カテゴリ別の件数、受注と失注の比較)と、月ごとの件数の推移だけ。
  装飾は付けない。図にも、件数を表示する

`analysis.md` の構成(1〜2ページ):

1. この分析の範囲と限界(対象ルーム、期間、件数、書き手の主観)
2. 結果の要点(数字で、5行以内)
3. 失注の理由(順位と、代表的な言い回し)
4. 受注の決め手(失注との比較)
5. 気づいたこと(解釈)と、改善の提案
6. 確認が必要なこと(要確認の件数、記載なしの件数、あやしい点)

## 7-3. 正解データと、検証(ステップ4で行う)

私が、**既に知っている受注/失注の例を、5〜10件**渡す(会社名と理由)。それを使って確かめる。

1. **取りこぼしの確認**:正解データの会社が、すべて表に出ているか。出ていなければ、なぜ拾えなかったか
   (キーワード、期間、ルーム、文脈の切り方)を報告して、拾い方を直す
2. **正しさの確認**:表からランダムに20行を選び、「理由(要約)」と「元の文」を並べて、私に見せる。
   私が、合っているか判定する。間違いの傾向(会社の取り違え、結果の取り違え、理由の言い過ぎ)を、
   拾い方の改善に使う
3. **言い過ぎの確認**:理由(要約)が、元の文に書かれていない内容を含んでいないか、全行を機械的に確認する
   (要約の中の固有名詞・数字が、元の文にあるか)。ないものは、推測メモに移す
4. **件数の確認**:候補の数 → 対象外の数 → 表の行数、が合っていること(増減の理由を説明できる)
5. **重複の確認**:同じ会社・同じ結果が、別の行に分かれていないか
6. **個人情報の確認**:表の中に、顧客の個人名・電話番号・メールアドレスが残っていないか
