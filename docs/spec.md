# 補助金レーダー 仕様書(依頼文の保存版)

物件王(株式会社物件王)の社内ツール。補助金・助成金の情報を、毎日自動で集め、通知し、いつでも一覧で見られる仕組み。
※認証情報は含めない。依頼文の全文を保存したもの。

## 1. 目的と、使われ方

- 使う人:物件王の社員(セールスグロース、営業、CS)。**社内専用。**
- 物件王は、建築・リフォーム・不動産の会社(加盟店)に、補助金・助成金の活用を支援している
  (例:デジタル化・AI導入補助金、人材開発支援助成金)。お客様に、「いま使える制度」を、早く、正確に案内したい
- 困っていること:新しい公募の開始、締切の近い制度、制度の数字の変更を、毎日探すのが大変で、見落とす
- ほしいもの:
  1. **毎朝の通知**:新着、締切が近いもの、制度の更新を、1通にまとめて
  2. **いつでも見られる一覧**:絞り込み・検索ができ、気になるものに印を付けられる
  3. **制度の更新の検知**:決まった公式ページが変わったら、変わった部分を知らせる

## 2. 絶対に守ること

1. **費用がかからない方法で作る。** 有料のサービス・有料のAIのAPI・有料のホスティングは使わない。費用が出そうな点が見つかったら、作る前に、依頼者に言う
2. **公式の情報(国・自治体・公的機関)を、基本にする。** 民間のまとめサイトは、自動で取らない(利用の決まりがあるため)。取るサイトは、すべて、**利用規約・robots.txt・APIの利用条件を確認**して、自動取得してよいことを確かめてから、使う。確認できないサイトは、使わず、依頼者に報告する
3. **取得の頻度を抑える。** 1つのサイトへの1日の取得は、必要最小限(1日1回が基本)。相手のサイトに、負荷をかけない。取得の間に、待ち時間を入れる。失敗しても、繰り返し叩かない
4. **本文を丸ごとコピーして保存・表示しない。** 保存・表示するのは、タイトル、実施機関、公開日・更新日、受付期間、上限額、対象、ごく短い抜粋(1〜2文)、元のページへのリンク。出典(サイト名)を必ず付ける
5. **通知・一覧に出す情報は、公開されている情報だけ。** お客様の名前・数字は入れない
6. **認証情報(APIトークン、メールの設定など)を、コード、ログ、ドキュメント、チャットに書かない。** スクリプトのプロパティなど、安全な場所に置く
7. **Chatworkなど外部への送信は、最初は、依頼者宛てのテストだけ。** 本番の宛先への送信は、依頼者が確認してから。送る相手と部屋は、依頼者が決めたものだけ
8. **正確さを優先する。** 日付・金額・対象は、元のページに書かれているとおりに保存する。読み取れないものは、空欄にして、「要確認」と表示する(推測で埋めない)
9. 分からないことは、推測で埋めず、質問する

## 3. 集める情報源(候補。**最初に、使ってよいかを確認する**)

情報源ごとに、次を調べて、表で出す:取れる方法(API / RSS / ページの取得)、利用の決まり、取れる項目、更新の頻度、取得の難しさ。

### 3-1. 補助金の一覧(新着・募集中)

| 候補 | 内容 | 方法の見立て |
|------|------|--------------|
| Jグランツ(デジタル庁) | 国・自治体の補助金の募集情報 | 公開のAPI:一覧取得 `GET https://api.jgrants-portal.go.jp/exp/v1/public/subsidies`、詳細 `/v1/public/subsidies/id/{id}`(または`/v2/…`)。**認証・パラメータ・更新日での絞り込み・利用条件・上限は、デジタル庁の公式のAPI仕様(`jgrants-api.yaml`)と利用案内で確認する** |
| J-Net21(中小機構)の支援情報 | 補助金・助成金・融資などの支援情報 | RSSがあるか、ページの取得が許されるかを確認 |
| 中小企業庁・経済産業省の新着 | 中小企業向けの補助金の公募開始・採択結果 | RSSの有無を確認 |
| 国土交通省の新着 | 住宅・建築・不動産関連(省エネ、住宅リフォーム、空き家、耐震、長期優良住宅 など) | RSSの有無を確認 |

### 3-2. 助成金(厚生労働省・労働局)

| 候補 | 内容 | 方法の見立て |
|------|------|--------------|
| 厚生労働省:雇用関係助成金(人材開発支援助成金、キャリアアップ助成金、業務改善助成金 など)の新着・更新 | 制度の改正、様式・パンフレットの更新 | 新着のRSS、またはページの更新検知 |
| 愛知労働局・岐阜労働局 | 地域の案内・説明会 | ページの更新検知 |

### 3-3. 地域(自治体)

物件王は、名古屋・岐阜が拠点。加盟店の所在地の都道府県も対象にする(「10」の質問)。

- 愛知県、岐阜県、名古屋市、岐阜市の、中小企業向け補助金のページ(新着の一覧)
- 加盟店の多い都道府県・市区町村(あれば)

### 3-4. 制度の更新を、特に見る公式ページ(ウォッチ対象)

制度の数字・要件が変わったら、すぐ気づきたいページ。**ページの本文が変わったか**を、毎日見る。

- 人材開発支援助成金(厚生労働省のページ、令和8年度のパンフレット、支給要領のPDF)(→ 助成金シミュレーターの、制度の数字の表を見直すきっかけ)
- デジタル化・AI導入補助金(公式サイト、公募要領、スケジュール、更新履歴)
- キャリアアップ助成金、業務改善助成金のページ
- 依頼者が追加を望むページ(設定のシートに、URLを足すだけで、増やせる作り)

更新を検知したら、**変わった部分(追加された行・削除された行の、短い抜粋)と、元のリンク**を、通知に出す。
PDFは、中身の差分が取りにくいので、ファイルの更新日時・サイズ・ハッシュが変わったことを、知らせる。

## 4. 関係の深さ(スコア)と、絞り込み

多すぎる通知は、読まれなくなる。**関係の深さを点数にして、通知は、上位だけにする。**
点数のつけ方は、設定のシート(「キーワードの表」)で、コードを触らずに直せるようにする。

| 点数を足す条件(初期値のたたき台。依頼者が直す) | 例 |
|------------------------------------------|----|
| 物件王が扱う・勧めている制度 | デジタル化・AI導入補助金、IT導入補助金、人材開発支援助成金、人材育成支援コース、リスキリング、キャリアアップ助成金、業務改善助成金 |
| 加盟店の業種 | 建設、工務店、リフォーム、住宅、不動産、空き家、省エネ、断熱、耐震、長期優良住宅、ZEH |
| 中小企業向けの、広く使える制度 | 小規模事業者持続化補助金、ものづくり補助金、新事業進出補助金、省力化投資、事業承継・M&A、賃上げ |
| 地域 | 全国 / 愛知 / 岐阜 / 加盟店の所在県 |
| 対象 | 中小企業・小規模事業者・個人事業主であること |

点数を引く条件(関係が薄いもの):農林水産業のみ、医療・福祉のみ、学校・NPOのみ、個人向けのみ、など。

- 点数で、3段に分ける:**高(通知に載せる)/ 中(通知に、件数だけ。一覧では見られる)/ 低(一覧のみ)**
- 「高」「中」の境目は、最初の1週間は、依頼者と見ながら調整する(多すぎれば上げ、少なすぎれば下げる)
- 点数の理由を、一覧に表示する(「物件王の扱う制度」「地域:愛知」など)。なぜ上に出たか、分かるように

## 5. 保存するデータ(新しいスプレッドシート「補助金レーダーDB」)

元のシートや、既存のファイルには書き込まない。新しく作る。表(タブ)ごとに、1つのテーブル。編集は、画面とスクリプトからだけ。

| タブ | 内容 |
|------|------|
| 制度 | ID(情報源+元のID)、名前、実施機関、種別(補助金 / 助成金 / その他)、地域、対象、上限額・補助率、受付開始、受付終了、公開日、更新日、元のリンク、出典、短い抜粋、点数、点数の理由、状態(募集中 / 予定 / 終了)、初めて見つけた日、最後に見た日、内容のハッシュ |
| 更新の履歴 | 制度ごとの、変わった項目(例:受付終了日が変わった)、前の値、後の値、検知した日 |
| ウォッチ | 3-4のページ。URL、名前、最後に見た日、本文のハッシュ、最後の差分 |
| 通知の履歴 | いつ、どこへ、何件、成功/失敗 |
| 実行の記録 | 日ごとの、情報源ごとの、取得件数・エラー・所要時間 |
| 設定 | キーワードの表、通知先、通知の時刻、ウォッチのURL、情報源のON/OFF |
| 気になる | 制度ID、印(気になる / 対応中 / 対応済 / 見送り)、メモ、付けた人、日付 |

- 同じ制度を、**情報源をまたいで重複させない**(名前・実施機関・受付期間が近いものは、「同じ可能性」として、まとめる。確実でなければ、別に残し、重複の候補として表示する)
- 受付終了から一定期間(例:90日)たったものは、「アーカイブ」に移す(消さない)

## 6. 通知

### 6-1. 毎朝の通知(1日1通。まとめて)

時刻:朝(依頼者が決める。初期値は、平日・休日とも、7:30)。

内容(上から):

1. **制度の更新**(ウォッチ対象が変わったもの):名前、変わった部分の短い抜粋、リンク。**全件、載せる**
2. **締切が近いもの**:7日以内、3日以内、前日。物件王に関係が深い(点数「高」)ものだけ
3. **新着(点数「高」)**:最大10件。名前、実施機関、受付期間、上限額、点数の理由、リンク
4. **点数「中」**の件数と、一覧へのリンク
5. 下に:今日の取得結果(どの情報源が、取れた / 取れなかった)。**取れなかった情報源があれば、目立つ位置に出す**(黙って抜け落ちるのを防ぐ)

- 該当が1件もない日も、「本日の新着なし」と、1〜2行で送る(動いていることが分かるように)。※送らない設定も、設定のシートで選べるようにする

### 6-2. 送り先(依頼者が決める。費用のかからない方法から)

| 方法 | 費用 | 注意 |
|------|------|------|
| メール(Google Workspaceのメール送信) | 無料(1日の送信数に上限。上限を確認して、表で出す) | まず、これを基本にする案 |
| Chatwork(APIで、通知用の部屋へ投稿) | APIが、現在のプランで使えるか・無料かを、確認する | 本番の部屋への送信は、依頼者が確認してから |
| Googleチャット・Slackなど | 使っていれば、確認 | |

- 通知の中に、個人情報・お客様の情報は入れない(公開情報だけ)
- 通知の文面は、**スマホで、1画面で読める長さ**に。長い場合は、「続きは一覧で」とリンク
- 通知が失敗したら、管理者(依頼者)に、別の方法(メール)で知らせる

### 6-3. 緊急の通知(任意。依頼者が望んだ場合のみ)

「点数が非常に高い新規公募の開始」「ウォッチ対象の、制度の数字の変更」を、朝を待たずに、すぐ送る。
最初は、作らない。毎朝の通知を見てから、必要なら、追加する。

## 7. 一覧の画面(いつでも見られる)

- Google Apps Scriptのウェブアプリ(「組織内のユーザーのみ」で公開。@bukkenking.comのアカウントだけ)
- 画面:
  1. **今日**:今日の通知と同じ内容(新着・締切・更新)
  2. **一覧**:全件。絞り込み(状態、点数、種別、地域、受付終了までの日数、実施機関、キーワード)、並べ替え(締切が近い順、新着順、点数順)、検索
  3. **詳細**:項目、元のリンク、更新の履歴、点数の理由、「気になる」の印とメモ
  4. **制度の更新**:ウォッチ対象ごとの、差分の履歴
  5. **設定**(管理者のみ):キーワードの表、情報源のON/OFF、ウォッチのURL、通知先と時刻
- 「気になる」「対応中」「対応済」「見送り」の印と、メモを、複数人で共有して使える
- 締切までの日数を、大きく見せる(7日以内は強調。色だけに頼らず、文字でも「あと3日」と出す)
- 数字・日付が読み取れていないものは、「要確認」と表示し、元のリンクへ誘導する

## 8. デザイン

物件王のロゴの色と、BCB(物件王のデザインの知見)の方針で作る。BCBのスキルが使える環境なら、使ってよい。
ロゴ(`logo_bukkenking.png`)は、作業フォルダに置いてある。

- 色:ロゴのティール `#05968C`、ロゴの文字の濃いグレー `#374141`(純黒は使わない)。白地の小さい文字には `#05968C` は明るさが足りない(白との差3.65:1。基準4.5:1)ので、文字・ボタンには、少し濃いティール(例 `#04746D`。白との差5.64:1)を使う。値は、実際に計算して確かめる
- 色の割合:背景・面 70〜90% / メイン(ティール)10〜20% / アクセント 5〜10%(1色。いちばん大事な操作、または、「あと◯日」の強調にだけ。ロゴに無い色なので、色相の違う2〜3案を、モックで見せて、依頼者が選ぶ)
- フラット。影をつけない。区切りは、細いグレーの線。角丸は、決まった4段階を、同じ役割に同じ値で使う
- 状態(募集中 / 予定 / 終了、点数の高中低、締切の近さ)の色は、意味ごとに固定し、必ず、文字(ラベル)や形も付ける。メインのティールと、混同しない
- 大きな数字(締切までの日数、新着件数)を、強調。日付は「2026/12/01(あと13日)」の形
- 一覧は、情報量が多いので、**文字の大きさと余白を、読みやすさ優先**に。スマホでは、カード型
- 見出しは日本語。飾りに、小さな英語を添えてよい。AIが作ったような見た目(派手なグラデーション、ぼかし、過剰なアイコン)は避ける
- 入力欄に、見えるラベルを付ける。エラーは、責めずに、直し方を書く。キーボードだけで操作でき、フォーカスが見える
- 通知のメールの見た目も、同じ色・同じ見出しの付け方にそろえる(装飾は最小限。読みやすさ優先)

## 9. 技術(費用ゼロ)

- **実行の場所:Google Apps Script**(時間トリガーで、毎日、決まった時刻に実行)。Google Workspaceの、いまの契約の範囲で使える
- **データの置き場:新しいスプレッドシート「補助金レーダーDB」**(5)
- **取得**:`UrlFetchApp`で、APIまたはページを取得。**Apps Scriptの上限**(1回の実行時間、1日の取得回数、トリガーの合計時間、メールの送信数)を、公式の資料で確認し、**予想の使用量との表**を作って、余裕があることを示す。1回の実行が長くなる場合は、情報源ごとに分けて実行する
- **ページの取得**:HTMLから、必要な部分だけを取り出す。サイトの作りが変わると、取れなくなる。そのため、**取り出す部分の指定(セレクタなど)は、情報源ごとに1か所にまとめ、直しやすくする**。取れなくなったら、通知に出す(6-1の5)
- **重複・更新の検知**:情報源ごとのIDまたはURLをキーにして、内容のハッシュで、変わったかを見る。同じ日に何回実行しても、結果が同じになる(冪等)
- **コード管理**:ローカルで、claspで管理。ソースは、非公開のリポジトリ(無料)
- **認証情報**:スクリプトのプロパティ。スクリプトの編集者は、必要な人だけ
- **ログ**:実行の記録に、情報源ごとの、取得件数・新着件数・エラー・所要時間を残す。個人情報・認証情報は、残さない

もし、Apps Scriptの制約(取得できない、時間が足りない、など)で、実現できないと分かった場合は、作り始める前に、費用のかからない代わりの方法(例:GitHub Actionsの無料枠での定期実行)を、費用・できること・手間の表で比べて、提案する。勝手に変えない。

## 10. 先に確認したいこと(最初に、依頼者に質問する)

**一度に5問まで、見立てを添えて**聞く。

1. 通知の送り先と、受け取る人:メール(誰に)/ Chatwork(どの部屋)。時刻(見立て:最初は、依頼者宛てのメールだけでテストし、1週間後に、チームへ広げる)
2. 関係が深い制度と、キーワードの初期値(「4」の表)。物件王が、お客様に勧めている制度の名前
3. 地域:名古屋・岐阜のほかに、加盟店の多い都道府県(エリア調査シートの加盟店一覧から、都道府県の一覧を作ってよいか。作る場合、**加盟店の名前・住所は、使わず、都道府県の件数だけ**を使う)
4. ウォッチするページの初期値(3-4)。ほかに、毎日見たいページ
5. 「一覧の画面」(7)は、最初から必要か。まず、通知だけで始めてよいか
6. 要約を、将来、入れたいか(入れるなら、費用のかからない方法を、一緒に考える)

## 11. 正解データと、検証

### 11-1. 「取れているか」の確認

1. 情報源ごとに、取得件数が、ゼロでないこと。ブラウザで、元のサイトの一覧と見比べて、**ランダムに10件、名前・受付期間・上限額が、一致すること**
2. 依頼者が、**いま募集中・近日中に始まる、と知っている制度を、5件**教える。それが、一覧に出ること(取りこぼしの確認。出ない場合は、なぜ取れなかったかを報告する)
3. 参考:依頼者の補助金の進捗表では、デジタル化・AI導入補助金の7次の、申請締切が12/1、採択発表が1/19、実績報告締切が7/30。公式の公募ページで確かめたうえで、一覧に、7次の締切が出ること(出ない場合は、情報源の範囲を見直す)

### 11-2. 「正しく扱えているか」の確認

4. 日付の読み取り:和暦(令和8年)、年なし(12/1)、期間(〜まで)、「随時」「予算がなくなり次第」など、いろいろな書き方が、正しく日付になるか。読み取れないものは、「要確認」になること(推測しない)
5. 重複:同じ制度が、複数の情報源にあるとき、重複の候補になること。完全に同じものが、2行にならないこと
6. 更新の検知:テスト用に、ウォッチ対象の保存済みの本文を、わざと書き換えて、差分が検知され、変わった部分の抜粋が、通知に出ること。変わっていないときは、通知に出ないこと(誤検知が少ないこと。日付・アクセス数・広告など、毎日変わる部分は、除外する)
7. 同じ日に、2回実行しても、通知が2通にならず、データも、増えないこと
8. 点数:点数の理由が、毎件、表示されること。キーワードの表を変えると、点数が変わること(コードを触らずに)

### 11-3. 「毎日、動き続けるか」の確認

9. 時間トリガーが、決まった時刻に動き、**1週間、連続で、失敗なく**通知が来ること(テスト期間。依頼者宛て)
10. 情報源の1つを、わざと取得できない状態にして、通知に「取れなかった」と出ること(黙って抜け落ちない)
11. Apps Scriptの上限に対して、1日の使用量が、余裕を持って収まっていること(表で示す)
12. 通知が、スマホで、1画面で読める長さであること。リンクが、正しく開くこと
13. 社内専用であること:ログインしていない状態・社外のアカウントでは、一覧の画面も、データも、見られないこと
14. 費用:使ったサービス・機能の一覧を出し、すべて無料の範囲であることを示す

## 12. 進め方

各ステップの終わりに、結果を依頼者に見せて、承認をもらってから次へ。

- **ステップ0:情報源の確認(コードを書かない)**:3の表(取れる方法、利用の決まり、取れる項目)、Apps Scriptの上限の表、通知の方法の確認、質問(10)
- **ステップ1:収集とデータ**:承認された情報源から集め、データベースに保存。点数(4)。確認(11-1、11-2)
- **ステップ2:通知(依頼者宛てのテスト)**:毎朝の通知を、依頼者だけに、1週間。文面と点数の調整(11-3)
- **ステップ3:チームへ**:依頼者が決めた相手に広げる(Chatworkの本番の部屋への送信も、ここで、依頼者の確認を取る)
- **ステップ4:一覧の画面**(7):依頼者が必要と決めたら
- **ステップ5:運用**:週1回、「取れなかった日」「誤検知」「点数の調整」を振り返る。情報源の追加・変更の手順を、`README`に書く
- **(依頼者が望んだ場合のみ)ステップ6:要約**:費用のかからない方法で、検討

## 13. 最初にやること

1. このプロンプト全体を、作業フォルダに`docs/spec.md`として保存する(認証情報は含めない)
2. ステップ0を実行する。まず、3の情報源の確認の表を、依頼者に見せる
3. 依頼者の承認まで、ステップ1のコードは書かない
